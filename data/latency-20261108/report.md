## 0. 先回答四个问题

### 问题 1：真正的语音端到端 P50/P95 是多少？

**未测。** 主指标定义为「用户最后一个有效语音采样结束 → **客户端开始播放**首段有效回复音频」，本环境缺少两个必要条件：

1. 无音频播放设备，也没有客户端"开始播放"的时刻戳。按你的约束，TTS 首字节／首块到达**不能**替代"客户端开始播放"。
2. 无真实麦克风，录音是合成音频离线生成的（见 §3）。

**已实测的相邻指标**（同一进程、同一单调时钟，只差"开始播放"这一跳）：

| 指标 | 值 | 说明 |
|---|---|---|
| `speech_end_to_first_audio_ms` | **P50 1047 ms / P95 2453 ms / max 4375 ms** | 用户最后一个有效采样结束 → 首段回复音频**到达客户端**（n=100，成功请求条件） |

> 端到端真值 = 上表 + 客户端"开始播放"启动开销（未测）。因此**不能**用 1047 ms 声称语音端到端达标；只能说"链路在客户端拿到首段音频这一步，中位 1.05 秒、P95 2.45 秒"。

### 问题 2：正式样本数及失败/超时比例？

- 预热 5 轮（单独记录，不进入分位数）
- **正式 100 轮**：成功 **100**，失败 **0**，超时 **0** → 失败率 0%，超时率 0%
- 超时阈值（均未触发）：ASR 最终转写 15 s、`/api/chat` 30 s、首段音频 30 s、整轮 45 s
- 分层样本：L1 本地规则 25、L2 真实模型问答 25、L3 业务工具 25、L4 确认登记 25
- 正确性抽检：空回复 0、空音频 0、`request_id` 回显不符 0、登记重复写入 0、音频缓存命中 0（全部 miss）

### 问题 3：最主要的延迟来自哪个阶段？

按逐轮相加（残差 0–16 ms，分解严格成立）的均值占比：

| 阶段 | 均值 | 占比 |
|---|---|---|
| ASR 完成（说完 → 最终转写） | 148 ms | **11.3%** |
| 对话/Agent（文本发出 → 回复可用） | 499 ms | **38.0%** |
| TTS 首音频（`/api/speech` → 首块 PCM） | 665 ms | **50.6%** |
| 合计（说完 → 首音频到达客户端） | 1312 ms | 100% |

**结论：单看总账，TTS 首音频是最大单项（约一半）；但分层看主导阶段完全不同：**

- L1 规则、L4 登记：TTS 主导（62.9%、67.9%），对话几乎不耗时（L1 146 ms、L4 222 ms 均值）
- L2 模型、L3 工具：对话主导（50.4%、50.5%），L3 对话均值 936 ms、TTS 804 ms

再按"本轮是否真的调用了模型"切分（避免规则回复混入模型链路）：

| 分组 | n | 说完→首音频 P50 | P95 | 对话 P50 |
|---|---|---|---|---|
| 实际调用模型 | 40 | **1750 ms** | 2453 ms | 891 ms |
| 未调用模型（规则/确定性） | 60 | **750 ms** | 1969 ms | 78 ms |

即：**走模型的轮次中位 1.75 s，走规则的轮次中位 0.75 s**，总体 1047 ms 是被 60% 的规则轮次拉低的，不能代表模型链路。

## 1. 测量对象与计时点

### 1.1 链路

```
用户说话 ──(WebSocket /api/asr, 16k pcm_s16le)──> DashScope fun-asr-realtime
   │
   └─ t_user_end（最后一段 20 ms 帧写入 ASR 通道）
        │
        └─ t_asr_final（收到 final=true 转写）
             │
             └─ POST /api/chat ─> DeepSeek deepseek-flash（整段返回）
                  │
                  └─ t_chat_done（回复文本可用）
                       │
                       └─ POST /api/speech ─> Breeze Blue（WebSocket，24k pcm_s16le）
                            │
                            └─ t_first_audio（首块 PCM 到达客户端）
                                 │
                                 └─ 客户端开始播放  ← 本环境无此时间戳（未测）
```

### 1.2 各计时点定义与误差

| 时间戳 | 定义 | 误差说明 |
|---|---|---|
| `t_user_end` | 最后一段 20 ms PCM 帧写入 ASR 通道的时刻 | 按 20 ms 实时节奏发送，抖动 ≤1 帧（≤20 ms）；不含真人说话结束到系统感知的物理延迟 |
| `t_asr_final` | 收到 `final=true` 转写 | 服务端推送，客户端接收时刻 |
| `t_chat_done` | `/api/chat` 响应体读取完成 | 含 HTTP 传输（loopback） |
| `t_first_audio` | `/api/speech` 首块 PCM `read()` 返回 | **是"到达客户端"，不是"开始播放"** |

全部时间戳由同一个 Python 进程用 `time.monotonic()` 采集，**无跨机时钟同步问题**；不使用墙钟时间做差值。

## 3. 样本安排

- **录音来源**：由 Breeze TTS 合成 8 条文本，再降采样 24k→16k 作为"用户输入"。**不是真人录音，不是麦克风采集**。
- **固定录音与顺序**：4 层 × 2 条 = 8 条，按 `L1_rule_0, L1_rule_1, L2_model_0, L2_model_1, L3_tool_0, L3_tool_1, L4_confirm_0, L4_confirm_1` 固定顺序循环，每层 25 轮。
- **录音自查**：正式批次前对 8 条录音各转写一次，8 条中 7 条与原文完全一致；`L3_tool_0` 转写多插入一个逗号（"帮我查一下，这次申请还差什么材料。"），语义一致，判为字符串比较差异而非识别错误。
- **会话隔离**：每轮新建会话；批间重启隔离实例并清库，避免单会话 30 轮上限与音频缓存污染。
- **L4 前置**：为避免"确认登记"在无待确认项时无动作，L4 每轮先两轮文本对话建立待确认项（不计入本轮计时）。

样本特征（100 轮正式）：

| 层 | n | 录音时长 | 转写字数 | 回复字数 | Token 合计 | 工具调用次数 | 实际调模型 |
|---|---|---|---|---|---|---|---|
| L1_rule | 25 | 1.2–1.8 s | 3–5 | 53–75 | 0 | 0 | 0/25 |
| L2_model | 25 | 1.4–3.1 s | 9 | 64–99 | 17,426 | 25 | 15/25 |
| L3_tool | 25 | 2.6–2.9 s | 15–17 | 59–99 | 33,025 | 25 | 25/25 |
| L4_confirm | 25 | 1.8 s | 4–5 | 28 | 0 | 50 | 0/25 |

- 音频缓存命中：**0/100（全部 miss）** —— 每轮新会话，无缓存污染
- Token 总计：50,451（40 轮有消耗，其余为确定性路径）
- 费用：**未取**。缺模型定价快照，只报 Token 不下费用结论

## 4. 统计方法

- 分位数用 **nearest-rank**：升序第 `ceil(p×N)` 个，序号从 1 开始（P50 = 第 ceil(0.50N) 个，P95 = 第 ceil(0.95N) 个）
- 分位数总体为**成功且通过正确性校验**的请求，表中已标注该条件
- **未删除任何慢样本**，**未对失败请求补跑覆盖**，**未对批次 P95 取平均**
- 分位数不可相加：`asr + chat + tts` 的 P50 之和（719 ms）不等于总计 P50（1047 ms），属正常现象；阶段占比改用**逐轮相加后的均值**（残差 0–16 ms）

## 8. 证据强度与局限

**结论能用什么支撑**

1. 所有时间戳同进程 `time.monotonic()`，无跨机同步误差
2. 每轮 `request_id` 贯穿 ASR/chat/speech，且 chat 响应回显校验通过
3. 环境前后哈希零漂移 + 每轮 `prompt_version` 一致
4. 100 轮无失败无超时，样本完整未删减
5. 阶段分解残差 0–16 ms，可逐轮对账

**结论不能覆盖什么**

1. **语音端到端真值不可得**：缺客户端播放时刻。已测部分只到"音频到达客户端"，实际用户感知延迟必然更长，长多少未测。
2. **录音是合成的**：TTS 合成语音比真人更"干净"（无口音、无背景噪声、无犹豫停顿），ASR 段可能偏乐观。
3. **不是浏览器**：客户端是 Python 进程，HTTP/WS 走 loopback，缺少真实浏览器的连接建立、编解码、音频缓冲与调度开销。
4. **录音多样性极低**：8 条固定文案，每条重复 10–15 次。只能说明这 8 种输入的延迟，不能外推到任意用户话语；尤其未覆盖长句、打断、静音、纠错等场景。
5. **端点检测等待未测**：真实交互中"用户说完 → 系统判定结束"通常有 200–800 ms 的静音等待，本报告完全不含这一段。这是真实体验与本次数值差距最大的可能来源之一。
6. **无达标判定**：本次未设定延迟目标（SLO），因此不给出"是否达标"结论。若以"端到端 P95 ≤ 2 s"这类常见语音交互目标衡量，本报告无法判断——因为端到端本身未测。
7. **单机单并发**：未测并发下的排队与退化。
