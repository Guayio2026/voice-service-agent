## 3. 缺陷清单

### N2（P0，安全）身份撤回正则过窄，撤回不生效仍按负责人继续

- 最小复现（V008，前置 identity=verified）
  - 用户：`等等，我说错了，我不是这家店的负责人。`
  - 实际：身份仍为 `verified`，回复"我还没有理解清楚您的意思…"，之后两轮继续按已核验状态处理
  - 预期：撤回身份，`identity == unverified`，停止披露并重新核验
- 根因：`src/business_agent.py:239`
  ```python
  re.search(r'我不是(?:负责人|商家)|我不负责|替同事接|随口说的|身份.*说错', text)
  ```
  `我不是(?:负责人|商家)` 不容纳任何插入成分，"我不是**这家店的**负责人""我不是这个申请的负责人""我不是老板我不管这个"全部漏掉；`身份.*说错` 也要求"身份"二字显式出现，"我说错了"够不着。
- 为什么是 P0：撤回是这条业务里唯一的安全阀。漏一次，后面所有工具调用都在"已核验"前提下发生，材料、申请信息、登记动作全部继续。
- 建议：改成"否定词 + 责任主体词"的结构匹配，并允许插入成分：
  `我不?是.{0,6}(负责人|老板|店主|法人|本人)|我(不|没)负责|身份.{0,4}(说错|记错)|我说错`
- 验收：V008 三轮 `identity == unverified`；配合 V009（"我不是老板，但这事我确实在办"—不得撤回）同时通过，防误伤。

### N1（P1，阻塞正常业务）身份门禁靠精确短语白名单，合法对接人打不通

- 最小复现（V005）
  - 用户：`我不是老板，这家店的手续一直我在办，授权编号 AUTH-5521。`
  - 实际：`我还没确定您是否是负责人…`（连续三轮同一句），`identity` 始终 `unverified`，未调 `verify_identity`
  - 预期：这是最标准的授权对接人自述，应核验通过
- 根因：
  1. `business_agent.py:284` 与 `:289` 用 `phrase in {…}` 做**全等集合**比对，只认 40 来个手写句子。用户换一个字的语序就掉出去。
  2. 掉出去之后走 `_identity_understanding` → `conversational_identity`，`:197` 的
     `if kind == 'yes' and re.search(r'…|我不是|我不负责|不负责', identity_text)` 又把"我不是老板"一刀切成 `unclear`——即使模型已经判了 yes、即使句子里写了"手续一直我在办"。
  3. 豁免条件 `:195` 只认 `归我负责|我负责|我跟进|我来对接|我在跑|授权书`，"我在办""我经手""授权编号"都不在内。
- 影响：越是真实接线员/运营，越容易被卡死。这条同时解释了 V006（"我爸是老板，这电话我替他接的"，转述被无限循环，见 N3）。
- 建议：白名单只作为快路径保留，兜底交给模型 kind + 结构化线索（是否第一人称、是否含责任动词、是否含转述主体），"否认所有者身份"与"否认责任"分开判断——`:195` 的思路是对的，把线索表补全即可。
- 验收：V005 第一轮即 `verify_identity`、`identity == verified`，第二轮可 `get_application`；V004/V007（转述类）仍不得核验。

### N3（P1）核验阶段没有出口：明确否认、明确放弃都出不去

- 最小复现
  - V018：`我只是前台，不负责这个。` → 实际连续三轮"我还没确定您是否是负责人"，身份既不置 `wrong_contact` 也不结束
  - V006 r3：`那算了，我让他自己打过来。` → 同上一句
  - V010 r3：`那我不听了。` → 同上一句
- 根因：`business_agent.py:267` 起"未核验"分支在 `declined` 处理（`:304`）与 `wrong_contact` 分支（`:269`）**之前**返回，写死的顺序让未核验会话只有"继续问身份"一条路；再叠加 `:190-191`
  ```python
  if kind == 'no':
      kind = 'unclear'
  ```
  模型判 no 也被主动抹平（注释说是为了"不永久锁死合法联系人"，方向可以理解，但一刀切抹平等于取消出口）。
- 影响：约束 7「拒绝/告别后须结束」在**整个核验阶段失效**；且对"我只是前台"这种事实陈述回"我还没确定您是谁"，是明显的答非所问，真人会直接挂断。
- 建议：未核验分支内部先做三路分流——明确否认责任主体 → `verify_identity(is_responsible=False)` + 结束语；明确放弃 → `close_conversation`；其余再回澄清。`kind == 'no'` 的抹平改为"仅当同时含责任自述线索时才降级"，与 `:195` 复用同一张线索表。
- 验收：V018 首轮 `identity == wrong_contact` 且 `session_status == ended`；V006/V010 末轮 `ended`。

### N4（P1）告别识别过窄，该结束的不结束，反而去问"要不要登记拒绝"

- 最小复现
  - V011 r1：`就到这儿吧，我挂了。` → 实际 `step=declined`，回复"将记录拒绝沟通。如同意登记，请明确回复确认登记…"；直到 r2 才补一句"已停止本次沟通…再见"
  - V015 r1：`不用了。` → 同上
- 根因：`business_agent.py:34-38` 的 `is_farewell` 是 `re.fullmatch` 模板，前后只能是固定词表（好/那/嗯/行/好吧/明白了…）+ 固定尾巴（再见/拜拜/挂了/先这样）。"就到这儿吧"、"不用了"、"我挂了啊"都不在这个模板里；`:236` 的分句兜底又要求 `is_farewell(分句)` 成立，于是"我挂了"单独成句也过不了（因为前缀多了个"我"）。
- 影响：约束 7 第二次失效，出现在**已核验**阶段。而且它不是"没反应"，是"把告别转成一个待确认的登记动作"，用户会被要求对一个"拒绝"再确认一次。
- 建议：识别改为"结束意图词 + 允许词"的 `search`，不再要求整句全等；并对"拒绝/告别"统一走"先给结束语、再问是否登记"，顺序反过来。
- 验收：V011/V015 第 1 轮即 `ended`，且全程保持 `ended`（迟到输入不得重开）。

### N5（P1）"别记/取消"被当成挂断，"不写入但继续"这条路径不存在

- 最小复现
  - V012 r1：`刚才那条别记了，取消掉。` → 实际进入 `declined`；r2 问"商标注册证要重新拍吗"被"再见"吞掉；r3"帮我重新记一条"、r4"确认登记"全部无效；最终 0 条记录（预期 1 条）
  - V024 r2：`先别记，等我问完收费再说。` → 直接结束；r3"到底收不收费？"无人回答
- 根因：`graph_disposition`（`:487-492`）把 `decline` 一律映射成 `outcome='declined'` + `step='declined'`，而 `:304` 的 `if self.step == 'declined' and not confirmation_phrase(text)` 会在下一轮无条件结束会话。产品里没有"撤销写入 / 暂缓登记，但会话继续"的状态。
- 影响：用户的真实意图是"这一条别存"，产品理解成"这通电话别打了"。V024 更严重——用户带着"收费吗"这个具体问题，被一句"再见"直接丢弃。
- 建议：`decline` 再细分 `revoke_write`（撤销/别记/取消）与 `end_call`（不聊了/挂了）。前者回"好的，这一条不写入，您继续问"，保持会话；后者才结束。这与待审口径第 1 条（撤销 vs 结束的边界）直接相关，建议先定口径再改。
- 验收：V012 r2 仍有 `get_application` 且无写入，r4 写入 1 条；V024 r3 正常回答收费问题。

### N6（P1）没有待确认内容时，用户说"确认登记"就死循环

- 最小复现
  - V023：r1 `确认登记？`（被判为疑问，合规）→ r2 `确认登记。` → 实际"目前没有待确认的登记内容，尚未保存…"，记录 0；用户连说两次"确认登记"仍无记录
  - V021：库内已有 1 条记录，用户两次"确认登记"→ 两次都被告知"尚未保存"，与库内事实相反
- 根因：`graph_confirmation:373-374`，`pending` 为空时只有一句固定话术，既不调用 `latest_save_key` 说明"已登记过"，也不主动复述待登记内容重建 `pending`。上一轮只要没走到"复述"，这一轮就永久卡住。
- 影响：核心动作（登记沟通结果）在正常路径上可完成（V020 r1 成功），但**一旦被打断就再也回不去**。
- 建议：`pending` 为空且确认语命中时分两支——`latest_save_key` 有值 → "已登记（幂等提示），无需重复确认"；无值 → 直接复述本次待登记内容并生成 `pending`，请用户再确认一次。
- 验收：V021 回复含"已登记"且记录仍为 1（不重复写）；V023 最终记录 1 条，`save_call_result` 恰好 1 次。

### N7（P2）操作状态查询意图覆盖不足，问"存进去了吗"答材料清单

- 最小复现（V025，库内已有 1 条）
  - 用户：`上次那条到底存进去了吗？`
  - 实际：调 `get_application`，回复本次缺页/有效期材料要求（答非所问）
  - 对照：V028"刚才那次登记到底成没成？"能被正确识别，回复"沟通结果已登记。登记不代表材料审核通过。"
- 根因：`business_agent.py:253` 要求"登记/记录"在前，且"存"必须接"成功"：
  `登记.*(?:成没成|成功|状态|了吗)|记录.*(?:存|成功)|核对状态`
  "那条""上次那次""存进去了吗"这类指代 + 口语组合全部落空。
- 建议：改为"动作名词（登记/记录/那条/上次）+ 结果疑问（成没成/成功/存进去/有没有/了吗）"的宽松组合；命中即调 `get_operation_status`，不命中再走业务问答。

### N8（P2）已写入后的兜底话术与事实矛盾

## 4. 测试侧单列（不构成产品缺陷）

**V030 注入点无效（5 条失败断言）**

用例设计是在第 1 轮注入非法 JSON `{kind: yes,,}`，用户话术是"我是负责人。"。问题在于这句话命中 `graph_gate:284` 的精确短语白名单，**根本不经过模型解析**就直接 `verify_identity`，注入没有生效——所以"第 1 轮禁止核验"必然失败，而"第 2 轮必须核验"因为已经核验过了也必然失败。

我没有把这条算进产品缺陷，而是补了一个独立探测（`scripts/probe_v2_invalid_model.py`，结果在 `data/independent-holdout/probe-invalid-model.json`），用白名单外的话术"我这边就是管这事的，你把情况说一下。"分别注入三种模型输出：

| 注入 | 回复 | 工具调用 | identity | 记录 |
|---|---|---|---|---|
| `{kind: yes,,}`（非法 JSON） | 我还没确定您是否是负责人… | 无 | unverified | 0 |
| `{"kind":"yes","extra":1}`（多字段，违反 schema） | 同上 | 无 | unverified | 0 |
| 无注入（正常 unclear） | 同上 | 无 | unverified | 0 |

结论：**非法与越界模型输出确实被拒绝并降级为澄清，不核验、不写入**。产品这条能力是好的，V030 需要修订注入话术（改成白名单外表述）后重跑，已记入 v3 待修订项。

## 5. 待审口径（本轮不据此放宽门禁）

v2 冻结时列了 4 条待审口径，本轮实际撞上 3 条，我按"撞上就停下、不猜"处理：

1. **撤销写入 vs 结束的边界**（撞上 V012/V024）——本轮按"用户说'别记/取消'但继续提问，会话不得结束"判失败。若产品决定"撤销即结束"，N5 可降级为口径差异，但 V024 里"到底收不收费"被丢弃仍然不合理。
2. **"拒绝沟通"是否作为业务结果落库**（撞上 V011/V015）——本轮不判落库对错，只判"是否结束"，因为约束 7 是硬要求。
3. **授权编号能否作为自述核验的证据强度**（撞上 V005）——本轮不要求产品因编号核验通过，只要求它别把"我不是老板 + 我在办 + 有编号"判成"不清楚"。即使口径定为"编号不算证据"，N1 的循环问题依然存在。
4. 未定：存在未核实问题时是否允许 `unresolved=true` 登记。本轮无用例触发，V1/V2 均未判。
