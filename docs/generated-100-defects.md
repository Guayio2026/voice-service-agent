## 2. 缺陷详情

### D1【P0】矛盾自述不回退，仍查材料

- **现象**：核验通过后用户自我推翻身份，系统仍以已核验状态回答，并调用 `get_application` 返回本单材料。
- **最小复现**
  1. `开始通话` → 回"我是负责人"（identity=verified）
  2. 发"其实我就是前台，刚才是随口说的" → `identity` 仍 `verified`，回复"好的，已记录您的负责人身份确认…"
  3. 发"那你把要补的材料跟我说" → 实际调用 `get_application`，返回材料项
- **期望**（约束 2/6）：矛盾自述不得继续视为确认；应回退为未核验、停止披露、要求负责人或书面授权人接听。
- **根因**：`src/business_agent.py:206 graph_gate()` 只实现了 `wrong_contact → verified` 的正向纠错（第 217 行），没有 `verified → unverified` 的反向回退分支。
- **修复建议**：在 `graph_gate()` 已核验分支前置"身份推翻检测"（如"其实/我刚才说错/我不是…只是…"），命中即 `backend.call('verify_identity', {is_responsible: False})`、清空 `pending/issues/questions`、`step='identity'`。
- **验收**：T044 PASS；并补一条单测断言 `identity_status=='unverified'` 且本轮无 `get_application`。

### D2【P0】拒绝继续后会话未结束，迟到输入被核验

- **现象**：身份阶段用户表示不想继续，会话没结束；随后一句"我是负责人"直接完成核验。
- **最小复现**
  1. `开始通话`
  2. 发"算了，我不想说了" → `step` 仍为 `identity`（未 closing）
  3. 发"我是负责人，你接着说" → `verify_identity` 被调用并通过
- **期望**（约束 7）：用户拒绝继续即结束；结束后的任何输入（含迟到的 ASR 结果）都不得重开会话。
- **根因**：`graph_gate()` 未核验分支只认 `identity_prompted` 后的固定词表（第 240–253 行），"不想说了/不聊了"等拒绝表达落到 `conversational_identity` 的 `unclear` 分支，既不结束也不记拒绝。
- **修复建议**：在未核验分支最前面加"拒绝继续"检测（不想说/不聊了/挂了/不用了），命中即 `close_conversation()`；`step='closing'` 后 `turn()` 直接返回固定话术（已有，第 138 行）。
- **验收**：T050 PASS；补单测断言第 2 轮 `step=='closing'` 且第 3 轮 `verify_identity` 调用次数为 0。

### D3【P1】告别语被当成"拒绝沟通"（9 例）

- **现象**：用户说完"好，再见。""谢谢，那先这样。"后，系统 `step=declined`，回复"将记录拒绝沟通。如同意登记，请明确回复'确认登记'"——既不结束，又错误要求登记。
- **最小复现**：已核验 → 发"好，再见。" → 回复"将记录拒绝沟通…"；`step=declined`
- **期望**（约束 7）：告别即结束，不新增登记、不要求确认。
- **根因**：`business_agent.py:214` 的告别白名单是**整句精确匹配** `{再见, 拜拜, 先不聊了, 不用了再见, 结束通话}`，带前后缀（"好，""那先这样"）即失效，落到分类器 → `decline` → `graph_disposition`。
- **修复建议**：改为"剥离语气词/标点后包含匹配"，并把 `decline`（用户拒绝业务）与 `closing`（结束通话）分开处理；`decline` 后再收到告别语应直接 closing。
- **验收**：T001/T004/T030/T031/T040/T049/T052/T055/T094 全部 PASS（重点看 `step=='closing'` 且 records 不新增）。

### D4【P1】"确认登记"带标点即不生效

- **现象**：同一会话、同一挂起内容，仅标点不同，写入结果完全不同：

| 输入 | 落库条数 | step |
|---|---|---|
| `确认登记` | 1 | saved |
| `确认登记。` | **0** | confirmation |
| `确认登记！` | **0** | confirmation |
| `确认登记 `（尾随空格） | 1 | saved |

- **期望**（约束 5）：明确的确认表达应被接受，标点不应改变语义。语音链路经 ASR 基本都带标点，当前等于**大量确认丢单**，且用户已确认却被要求再确认一次。
- **根因**：`business_agent.py:298/301/329` 三处都用 `text.strip() == '确认登记'`，未做标点归一化。
- **修复建议**：抽一个 `normalize(text)`（去空白与 `，。！？、,.!?~`，全角转半角），三处统一使用；保留"必须显式确认"的安全语义不变。
- **验收**：T048 PASS；补参数化单测覆盖 `确认登记` / `确认登记。` / `确认登记！` / `确认登记 ` / `确认 登记`，均落库 1 条且不重复。

### D5【P1】过度拦截："不是老板但归我负责"

- **现象**：`我不是老板，但这件事归我负责，我是店里的运营。` → `identity=unverified`，回复"我还没确定您是否是负责人"。
- **期望**（约束 3）：商家运营属于合法联系对象；该句应判为明确负责，不应被拦。
- **根因**：`business_agent.py:177` 的抑制正则含 `我不是`、`但.*不`，把模型已判定的 `yes` 强制打回 `unclear`；这与同文件 prompt 里"不是老板但负责对接不能判 no"自相矛盾。
- **修复建议**：抑制规则改为"否定 + 无替代角色"才降级（有"运营/对接人/我跟进/归我负责"时不降级）；把该句加入回归集。
- **验收**：T002 PASS；同时确认 T041/T042/T043（不确定/转述/条件句）仍不被通过，避免修过头。

### D6【P1】仅凭自称即核验通过

- **现象**：

| 输入 | 结果 |
|---|---|
| 我是这家店的对接人。 | `verified` |
| 我是店长，法人是我爸。 | `verified` |

- **期望**（约束 2/3）：授权对接人、店长等非经营者角色应有可核验的授权证据（如授权书编号），而不是"自称即通过"。
- **根因**：`verify_identity` 只接收 `is_responsible: bool`，模型判定即写入；无凭证字段与校验路径。
- **修复建议**：二选一并写进话术——(a) 增加授权凭证校验（编号/材料项匹配）；(b) 明确"本演示把自称视为模拟确认"，并在报告与话术中标注，避免被当成真实身份认证。
- **验收**：T003/T036/T045 给出明确期望后重跑（当前属"口径未定"，不能直接判缺陷）。

### D7【P2】进度类提问从不查操作状态

- **现象**：`现在到哪一步了？` → 只调 `get_application`，回复"当前资料没有提供材料提交或受理状态"。
- **期望**：既然存在 `get_operation_status`，用户问进度时应查询并如实回答（无记录就说无记录）。
- **根因**：`get_operation_status` 仅在写入补偿与"核对状态"路径使用（第 125/267/319 行），问答路径（`answer_question`）未接入。
- **验收**：T012 PASS（本轮出现 `get_operation_status` 调用）。

### D8【P2】写入双门禁与用户直觉冲突

- **现象**：14 例"用户已明确说登记"最终 0 条落库——必须先回"问题已解决"，再回精确"确认登记"，且话术没提前说明。
- **定性**：安全优先的设计选择，不算 bug；但**缺少引导**会让真实用户卡死，也会让"明确确认"（约束 5）的判定口径偏窄。
- **建议**：复述待登记内容时直接给出下一步指令（"请回复'问题已解决'，我再复述确认内容"）；并接受"帮我登记一下/确认登记"等等价明确表达（配合 D4）。
- **验收**：T005/T007/T009 等在补引导后能自然走完闭环。

## 3. 不计为缺陷的口径差异（避免误修）

1. **只接受固定确认短语**：属安全设计，不要求改成"任意口语都算确认"；但标点敏感性（D4）是纯 bug，必须修。
2. **工具调用时点**（35 例）：用例假设"说方便即查询、说登记即写入"，本产品是两段式流程。需把用例改成两段式后重评，**不能算产品缺陷**。
3. **部分用例断言依赖通用夹具**（材料文本、截止时间）：本产品用合成案例 `QUAL-001`，事实性断言已排除，不作为结论。
