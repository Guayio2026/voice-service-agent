## 4. 产品缺陷清单（10 项）

### D1（P0）更正/否认负责关系后身份不撤销，继续披露本单材料

> 与 v2 的 N2 同源：撤回词表覆盖了"我不是负责人"，但不覆盖"不是我在管 / 不是老板 / 更正一下"。

- 用例：R010（3/3）、R011（3/3）
- 证据：两例前置均为 `identity=verified`；R010 用户"等下，我刚说错了，这店不是我在管"，产品回"我还没有理解清楚您的意思"或直接跳过，`identity` 三档全部保持 `verified`，第 2 轮回复含"商标注册证"；R011 更明确——话术已经说"原确认已失效"，但状态仍是 `verified`，第 2 轮继续披露，`get_application` 照调。
- 影响：`verified` 是披露闸门的唯一开关，这类"口头撤回"是真实来电中最常见的场景（接电话的是店员/家属/会计）。**话术与状态不一致比不撤回更危险**：用户已被告知失效，系统仍按已核验处理。
- 建议：撤回路径必须落库并阻断 `get_application` 与所有材料话术；撤回后同会话不得再回到 `verified`，除非重新走核验并有证据。

### D2（P1）模糊表态被当作负责人确认

- 用例：R005（3/3）
- 证据："大概算我管吧，老板基本不问这些" → `verify_identity(is_responsible=True)`，第 2 轮披露材料。第 2、3 轮用户被追问后升级为"我说了归我管""我是这家店负责这件事的人"，产品此时已不需要再听。
- 影响：与 D1 同族——核验门槛过低。真正确认应包含"明确自述 + 可核对的授权依据"，"大概/可能/算我"应触发追问。
- 建议：核验前加一层语义判定，模糊表述不计入确认；必要时要求授权编号或转人工。

### D3（P1）抱怨、否认缺项被判为"拒绝沟通"并单方面挂断

- 用例：R009（1/3）、R018（2/3）、R015（1/3）
- 证据：
  - R009："行行行，你们这套话术我服了" → "将记录拒绝沟通"；下一轮"说正事，材料到底缺哪些？" → "好的，已停止本次沟通；未新增演示记录。再见。"
  - R018："材料我早就都齐了，没什么要补的" → "将记录拒绝沟通"，后续被挂断。
  - R015："刚才那条不算，别存" → "将记录拒绝沟通"。
- 影响：把"情绪"和"业务分歧"记成"拒绝沟通"，既污染登记结果（`user_feedback` 失真），又提前终止仍有价值的通话。
- 建议：`declined` 只接受明确的"不沟通/不需要/别再打"类表达；抱怨、质疑、否认缺项必须先复述依据或转人工，且挂断前需二次确认。

### D4（P1）撤销登记 / 改写内容后，通话无法继续，新内容也无法登记

- 用例：R015（3/3）、R016（2/3）、C004（1/1）
- 证据：
  - R016 第 1 轮"先别存，我把话说清楚再记" → 正确进了"稍后联系意愿"待确认；第 2 轮"我要记的是：材料清单已经念给我听了" → 被判"您的陈述与系统资料可能存在差异，原确认已失效"；第 3 轮"确认登记" → "还有未解决的问题，不能登记通知完成"，最终 `records=0`。
  - C004 第 2 轮"改成'用户还有问题待核实'，先别按完成记" → "已取消这次待确认的登记，不会保存"；第 3 轮"确认登记" → 回到原复述再要求确认，"待核实"语义从未进入待确认内容，`records=0`。
- 影响：用户主动修正登记内容是高质量对话信号，现在被当成作废处理，等于把最准确的意图丢掉。
- 建议："改写"应替换待确认内容（保留轮次引用），"撤销"只清空待确认项、不清空对话能力；两者都不能导致挂断。

### D5（P1）未解决门禁没有出口，用户明确要求登记也无法完成

- 用例：R001（2/3）、R016（2/3）、C004（1/1）、S004（1/1）
- 证据：四处都出现同一句"还有未解决的问题，不能登记通知完成。请继续说明或请求人工核实；问题确实解决后请明确回复'问题已解决'"，同时 `pending=False`、`records=0`。用户已明确说"按'已通知完成'记一条""确认登记"，产品只给一条路：宣称问题已解决。
- 影响：门禁本身合理（防止把未解决记成完成），但**缺少"记为未解决"的通道**，结果是宁可什么都不记。真实场景下这等于把一次有效外呼变成零记录。
- 建议：门禁触发时必须给出两条可执行路径——"按'已通知、问题未解决'登记（`unresolved=true`）"或"转人工核实"；不能只留"说问题已解决"这一条。

### D6（P1）"收到通知但未补正"被落库为 `notification_completed` + `unresolved=false`

- 用例：C001
- 证据（五段比对）：用户意向"材料的事我收到了，但东西我还没补" → 复述段正确（两项缺项、依据齐全）→ 确认轮"确认登记" → `save_call_result` 实参 `candidate_outcome=notification_completed`、`unresolved=false`、`user_feedback=confirmed` → 库内记录同值。
- 影响：复述没错、落库失真，是最难靠人工抽检发现的一类。下游按 `unresolved` 统计催办量会直接失真。
- 建议：`notification_completed` 只能用于"已完成补正/问题已解决"；"仅收到通知"需要独立取值或 `unresolved=true`。

### D7（P1）取消话术与库内状态矛盾，且"还有没有"类问题不查操作状态

- 用例：C005、C003、S006
- 证据：
  - C005 第 1 轮"刚才那条取消掉吧" → "好的，已取消这次待确认的登记，不会保存"，但库内仍有 1 条记录（前置已写入）；第 2 轮"那系统里现在还有没有我那条？" → 未调 `get_operation_status`，答模板"操作状态只说明沟通登记是否保存，不是业务审核进度…"。
  - C003 两轮问"我这就算过了吧""登记和审核到底啥区别"，回复内容正确（明确否认审核结论），但从未查询操作状态。
  - S006 response_lost 后第 1 轮已自行补偿查询并确认落库，第 2 轮改靠内存状态回答。
- 影响：用户问"到底记上没有/取消了吗"是最高频追问，答非所问会被理解成敷衍；"不会保存"这类承诺在库内仍有记录时属于错误陈述。
- 建议：所有"是否已记录/是否已取消"的追问必须走操作状态查询后如实回答；不得用"不会保存"描述已存在的记录。

### D8（P2）授权编号不被采集，无编号时核验死锁

> 与 v2 的 N3（核验无出口）同源，只是这次发生在"用户主动给了授权编号"的场景。

- 用例：R003（1/3 稳定复现）
- 证据：用户两轮提供"授权书编号 AUTH-7F3C，你那边核一下"，attempt2 三轮回复同一句"我还没确定您是否是负责人。您也可以先问我是谁、来意或演示流程"，`verify_identity` 调用 0 次；attempt1/3 反而直接 `verified`，编号同样未被使用。
- 影响：编号是"授权对接人"这条业务约束的唯一外部证据，现在既不用它放行、也不用它拦。
- 建议：编号进入核验输入；无编号/编号不可验证时给出人工核实出口，不得复读同一句。

### D9（P2）撤回后凭一句自述恢复 `verified`

- 用例：R012（3/3）
- 证据：第 1 轮"我搞错了，我不是这家店的负责人" → "已撤回本次身份确认"（unverified，正确）；第 2 轮"不对，我又确认了一下，负责人确实是我" → 直接 `verify_identity` 通过（verified），无任何新证据；第 3 轮"你重新核一下不行吗"三次回复各不相同（建工单 / 披露材料 / 称资料差异）。
- 说明：这一条同时是**口径待审项**（见 §8 第 3 条）。产品当前选择"允许自述恢复"，但没有任何核验动作，等于给 D1/D2 留了后门。
- 建议：撤回后允许恢复，但必须重新走一次显式核验问句并留证。

### D10（P2）澄清话术复读，不回答用户的假设性问题

- 用例：R007（3/3 但断言未覆盖）、R003、R015
- 证据：R007 前两轮"如果这事儿真是我管的，那我是不是就得补材料？""假设我确实是负责人，你会先给我看哪几份？" → 两次同一句"我还没确定您是否是负责人"；R015 attempt2/3 第 3 轮"明白了，那重新记：沟通已完成" → "我还没有理解清楚您的意思"。
- 影响：断言没要求"答复相关性"，所以用例仍判 PASS；但观感上属于"装听不懂"，实际会推高转人工率。
- 建议：同一会话内同一澄清话术不得超过 1 次；澄清后必须回答用户已提出的问题（可按"未核验不能披露具体材料"的口径回答）。

7 条 BLOCKED 各自缺什么（不计入通过）：

| 用例 | 缺的能力 |
|---|---|
| S001 / S002 / S003 | 延迟投递：无法让某轮模型结果或工具回执延后到后续轮次到达 |
| S005 | 异步队列：无法在取消之后让排队中的写入继续执行 |
| S007 | 超时注入：后端只有 `query_fail` / `write_fail` / `response_lost`，没有"客户端超时且服务端结果未知" |

补齐优先级（按性价比）：延迟投递（`deliver_at_turn` 一行钩子可覆盖 S001–S003）→ 超时注入（`fault='timeout'`）→ 响应体替换（`response_override`）→ 异步队列与并发（成本最高，最后做）。

## 8. 待审项（需产品定口径，本轮无法判定对错）

1. **有未解决事项时能否以 `unresolved=true` 落库**——R001 / R016 / C004 / S004 全部卡在这一条。当前产品选择"一律不落库"，导致用户明确要求登记也记不上（D5）。
2. **"已收到/已了解"与"通知完成"的最小语义边界**——C001 的判定依赖这条口径：仅收到通知算不算 `notification_completed`。
3. **撤回身份后是否允许凭自述恢复**——R012：若允许，需要追加哪些核验动作；若不允许，需要什么断点保护。
4. **授权编号的证据强度**——R003：编号是否必须作为"授权对接人"的放行条件，编号查不到时走人工还是拒绝。
5. **"语义一致"的比对粒度**——是否要求 `issues_explained` 与复述逐项对应，还是只要求集合相等（C007 目前按集合判）。
6. **会话结束后的迟到输入如何处置**——S001–S003 补上延迟投递能力后，需要口径判断"结束后到达的模型结果/工具回执"是丢弃、补记还是重开。
